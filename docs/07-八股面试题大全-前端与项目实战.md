## 一、Vue3 前端

### 1. Vue3和Vue2的区别？

**答案**：

| 特性 | Vue2 | Vue3 |
|------|------|------|
| 响应式 | Object.defineProperty | Proxy（性能更好，支持数组/对象新增属性） |
| API | Options API | Composition API（逻辑复用更好） |
| 生命周期 | beforeCreate等 | setup中使用onMounted等 |
| 多根节点 | 不支持（需包裹） | 支持Fragment |
| 打包 | 全量 | Tree-shaking，按需引入，更小 |
| TypeScript | 支持一般 | 原生支持，类型更好 |
|  diff算法 | 全量diff | 静态提升 + PatchFlag优化 |
| 组合式 | mixins（命名冲突） | Composition API（清晰） |

---

### 2. Vue3的响应式原理？

**答案**：Vue3使用Proxy实现响应式。

**reactive**：
- 使用Proxy代理对象，拦截get/set/has/deleteProperty
- get时收集依赖（track），set时触发更新（trigger）
- 只能代理对象，不能代理基本类型

**ref**：
- 基本类型用ref，内部通过class的getter/setter实现
- 对象类型ref内部也用reactive
- 使用时需要.value（模板中自动解包）

**依赖收集**：
- effect函数执行时，设置activeEffect
- 访问响应式数据时，track收集effect到dep
- 数据变化时，trigger执行dep中的所有effect

**vs Vue2的defineProperty**：
- Proxy可以监听数组下标变化、对象新增属性
- defineProperty需要递归遍历所有属性，Proxy懒代理
- Proxy支持更多拦截操作

---

### 3. Composition API和Options API的区别？

**答案**：

**Options API**：
- 按选项组织：data、methods、computed、watch
- 逻辑分散在各个选项中，复杂组件难维护
- 逻辑复用用mixins，有命名冲突和来源不清晰问题

**Composition API**：
- 按逻辑组织，相关代码放在一起
- setup函数中定义响应式数据和方法
- 逻辑复用用自定义Hook（useXxx），清晰无冲突
- 更好的TypeScript类型推断
- 更好的Tree-shaking

**本项目使用Composition API + `<script setup>`语法糖**，代码更简洁。

### 4. Pinia和Vuex的区别？

**答案**：

| 特性 | Vuex | Pinia |
|------|------|-------|
| 状态 | state | state |
| 同步 | mutations | 无（直接修改state） |
| 异步 | actions | actions |
| 模块化 | modules嵌套 | 扁平，每个store独立 |
| TypeScript | 支持一般 | 原生支持，类型好 |
| 体积 | 较大 | 更小（1KB） |
| 组合 | 不支持 | 支持store间组合 |

**Pinia优点**：
- 去掉了mutations，直接修改state，更简洁
- 不需要嵌套模块，每个store独立
- 更好的TypeScript支持
- 支持插件扩展

**本项目使用Pinia**管理用户登录状态。

### 6. 前端路由的两种模式？

**答案**：

**hash模式**：
- URL带#，如http://xxx/#/home
- 原理：监听hashchange事件
- 优点：兼容性好，不需要服务端配置
- 缺点：URL不美观，SEO差

**history模式**：
- URL干净，如http://xxx/home
- 原理：HTML5 History API（pushState/replaceState + popstate事件）
- 优点：URL美观，SEO好
- 缺点：需要服务端配置（Nginx try_files指向index.html），否则刷新404

**本项目使用history模式**。

### 9. 什么是跨域？如何解决？

**答案**：跨域是浏览器的同源策略限制，协议/域名/端口任一不同即为跨域。

**解决方案**：
1. **CORS**：服务端设置Access-Control-Allow-Origin（本项目后端CorsConfig配置）
2. **代理**：开发环境Vite proxy（本项目配置/api代理到8081）
3. **JSONP**：只支持GET，已过时
4. **Nginx反向代理**：生产环境统一域名

**本项目**：
- 开发：Vite proxy（/api→8081，/agent→8000）
- 生产：Nginx反向代理，统一入口

## 二、项目实战高频面试题

### 11. 介绍一下你的项目？

**参考答案**：
这是一个企业级智慧医疗预约系统，采用前后端分离架构。后端Spring Boot 3 + Java 21，集成Spring Cloud Alibaba微服务生态（Nacos/Sentinel/OpenFeign）、MyBatis-Plus、Redis+Redisson分布式锁、RabbitMQ消息队列、多级缓存。前端Vue3 + TypeScript + Element Plus + ECharts，分患者端、医生端、管理端三端。另外有一个Python AI Agent服务，基于LangChain + RAG + Function Calling，为医生提供临床决策支持。

核心业务包括预约挂号（分布式锁防超卖）、缴费管理（延迟队列超时作废）、电子病历、处方管理、消息通知、AI智能助手。

### 12. 项目中遇到的最大挑战？怎么解决的？

**参考答案**：
最大的挑战是预约接口的并发超卖问题。多个患者同时预约同一医生同一时段，可能导致号源超卖。

解决方案：
1. 使用Redisson分布式锁，锁的粒度是"医生ID+日期+时段"
2. 加锁后二次校验号源数量（Double Check）
3. 数据库层面用乐观锁或唯一索引兜底
4. 接口加@Idempotent幂等注解防重复提交
5. 号源信息预热到Redis，减少数据库压力

---

### 13. 为什么用Redisson而不是自己写Redis锁？

**参考答案**：
自己写的Redis分布式锁（SETNX）有几个问题：
1. 不可重入：同一线程不能重复获取同一把锁
2. 锁续期：业务执行时间超过过期时间，锁被释放导致并发问题
3. 释放锁的原子性：判断+删除不是原子操作，可能误删别人的锁
4. 主从切换锁丢失

Redisson解决了这些问题：
1. Hash结构实现可重入（field=线程ID，value=重入次数）
2. 看门狗（Watchdog）自动续期，默认30秒，每10秒续期
3. Lua脚本保证释放锁的原子性（判断+删除）
4. 支持红锁（RedLock）解决主从问题
5. 支持公平锁、读写锁、联锁等丰富锁类型

---

### 14. 订单超时怎么实现的？

**参考答案**：
有两种方案，项目中都有实现：

1. **Redisson延迟队列**（当前使用）：
   - 创建订单时，将订单号投递到RDelayedQueue，延迟1天
   - 消费者从目标队列阻塞获取到期订单
   - 检查订单状态，若仍为待缴费则自动作废
   - 支付成功时从延迟队列移除

2. **RabbitMQ死信队列**（企业级方案，已配置）：
   - 订单消息发送到设置了TTL的队列
   - 过期后进入死信交换机→死信队列
   - 死信消费者处理超时订单

两种方案对比：Redisson简单但依赖Redis可靠性；RabbitMQ更专业，有持久化、重试、死信保障。

### 15. 消息通知为什么用RabbitMQ而不是直接发？

**参考答案**：
1. **异步解耦**：预约主流程不需要等消息发送完成，提升响应速度
2. **可靠性**：RabbitMQ持久化+手动ACK，保证消息不丢失
3. **削峰**：高峰期大量预约，消息队列缓冲
4. **重试机制**：发送失败自动重试，死信队列兜底
5. **解耦**：消息发送逻辑和业务逻辑分离，后续可扩展短信/邮件通知

**可靠性保障**：
- 生产者：Publisher Confirm + Returns
- MQ：队列持久化 + 消息持久化
- 消费者：手动ACK + 失败重试 + 死信队列

### 16. AI Agent是怎么设计的？

**参考答案**：
AI Agent采用ReAct（推理+行动）架构，基于LangChain实现：

1. **系统提示词**：设定医疗助手角色、能力、安全原则
2. **RAG知识增强**：用户问题先检索ChromaDB医学知识库，结果注入上下文
3. **工具调用**：定义7个工具（查询患者/预约/病历/药品/科室/知识检索/剂量计算），LLM通过Function Calling决定调用哪个
4. **ReAct循环**：LLM思考→调用工具→观察结果→继续思考→生成答案，最多5轮
5. **多轮记忆**：Redis存储对话历史，滑动窗口取最近10轮
6. **安全护栏**：所有回答加免责声明，不替代医生诊断
7. **流式输出**：SSE实时返回，前端逐字渲染

**和普通AI对话的区别**：普通对话只能基于训练数据回答，Agent可以调用工具查询实时的患者数据、预约信息，还能检索最新的医学指南，更实用。

### 17. RAG是怎么实现的？为什么不用微调？

**参考答案**：
RAG流程：
1. 离线：医疗文档切分→BGE嵌入模型向量化→存入ChromaDB
2. 在线：用户问题向量化→相似度检索Top-K→结果格式化→注入Prompt→LLM生成

**为什么不用微调**：
1. 成本：微调需要GPU和大量标注数据，成本高
2. 更新：医学知识更新快，微调重新训练慢，RAG只需更新知识库
3. 可溯源：RAG答案可追溯到具体文档，微调不行
4. 幻觉：RAG基于检索事实，幻觉更少
5. 适合场景：本项目是知识问答+数据查询，RAG更合适

### 18. 多级缓存是怎么设计的？

**参考答案**：
采用Caffeine + Redis两级缓存：

- **L1 Caffeine本地缓存**：缓存科室列表、字典数据等变化极少的热数据，30分钟过期，最大1000条，访问<1ms
- **L2 Redis分布式缓存**：缓存用户会话、预约状态、订单等需要共享的数据，1小时过期，访问~1ms
- **L3 MySQL**：持久化存储，~10ms

**一致性**：采用Cache-Aside模式，读时先查缓存，未命中查库并回写；写时先更新数据库，再删除缓存。

**为什么需要本地缓存**：减少Redis网络IO，降低Redis压力，热点数据访问更快。

### 19. 接口幂等性怎么保证的？

**参考答案**：
通过@Idempotent注解 + AOP + Redis SETNX实现：

1. 注解标注在需要幂等的方法上（预约提交、支付）
2. AOP拦截，根据SpEL表达式生成幂等Key（如方法名+用户ID+参数）
3. Redis SETNX设置Key，过期时间60秒
4. 设置成功：执行业务逻辑
5. 设置失败：抛出"重复提交"异常
6. 业务异常时删除Key，允许重试

**其他幂等手段**：
- 数据库唯一索引（预约表的患者+医生+日期+时段唯一）
- 订单状态机（支付接口二次校验状态）
- 分布式锁（预约接口的Redisson锁）

### 20. 接口限流怎么做的？

**参考答案**：
通过@RateLimit注解 + AOP + Redisson RateLimiter实现：

1. 注解参数：时间窗口、最大请求数、限流类型（IP/用户/全局）
2. AOP拦截，构建限流Key
3. Redisson RRateLimiter设置速率（令牌桶算法）
4. tryAcquire获取令牌，失败则抛出"请求过于频繁"异常

**应用场景**：
- AI对话接口：30次/分钟/用户
- 登录接口：IP限流，防暴力破解
- 预约接口：全局限流，保护数据库

### 21. 全局异常处理怎么设计的？

**参考答案**：
使用@RestControllerAdvice + @ExceptionHandler统一处理：

1. BusinessException：业务异常，返回错误码和信息
2. MethodArgumentNotValidException：参数校验失败，返回字段错误
3. MissingServletRequestParameterException：缺少参数
4. AccessDeniedException：权限不足，403
5. Exception：未知异常，记录日志，返回通用错误（不暴露堆栈）

**错误码设计**：
- 200成功
- 1xxxx系统级（参数错误、未登录、限流）
- 2xxxx用户级（用户不存在、密码错误）
- 3xxxx业务级（预约不存在、号源已满、订单异常）
- 4xxxx AI/第三方

### 24. 雪花算法生成订单号？时钟回拨？

**参考答案**：
雪花算法（Snowflake）64位组成：
- 1位符号位（0）
- 41位时间戳（毫秒级，可用69年）
- 10位工作机器ID（最多1024个节点）
- 12位序列号（每毫秒4096个ID）

**优点**：趋势递增、高性能、不依赖第三方、含时间信息

**时钟回拨问题**：
- 原因：服务器时钟同步导致时间倒退
- 解决：记录上次时间戳，若回拨时间小则等待，回拨大则抛异常或用备用机器ID
- 本项目SnowflakeIdGenerator有基础的回拨检测

- 统计：发送率、到达率、点击率

## 三、计算机网络与操作系统

### 29. TCP三次握手和四次挥手？

**答案**：

**三次握手**：
1. 客户端发SYN，进入SYN_SENT
2. 服务端回SYN+ACK，进入SYN_RCVD
3. 客户端发ACK，双方进入ESTABLISHED

**为什么三次**：两次无法确认客户端接收能力，四次没必要。

**四次挥手**：
1. 客户端发FIN，进入FIN_WAIT_1
2. 服务端回ACK，进入CLOSE_WAIT，客户端FIN_WAIT_2
3. 服务端发FIN，进入LAST_ACK
4. 客户端回ACK，进入TIME_WAIT（2MSL），服务端关闭

**TIME_WAIT为什么2MSL**：
- 保证最后一个ACK到达服务端（丢失则重传）
- 让本连接所有报文在网络中消失，避免影响新连接

### 30. HTTP和HTTPS的区别？

**答案**：

| 特性 | HTTP | HTTPS |
|------|------|-------|
| 端口 | 80 | 443 |
| 加密 | 明文 | TLS/SSL加密 |
| 证书 | 无 | CA证书 |
| 性能 | 快 | 略慢（握手开销） |
| 安全 | 不安全 | 安全 |

**HTTPS握手过程**：
1. 客户端发ClientHello（支持的加密套件、随机数）
2. 服务端回ServerHello（选定套件、随机数、证书）
3. 客户端验证证书，生成预主密钥，用公钥加密发送
4. 双方用随机数+预主密钥生成会话密钥
5. 后续用会话密钥对称加密通信

### 31. 进程和线程的区别？

**答案**：
- 进程：资源分配的最小单位，有独立地址空间，进程间切换开销大
- 线程：CPU调度的最小单位，共享进程资源，线程间切换开销小

**通信方式**：
- 进程间：管道、消息队列、共享内存、信号量、Socket
- 线程间：共享变量、wait/notify、锁

### 32. 进程间通信方式？

**答案**：
1. 管道（Pipe）：半双工，父子进程间
2. 命名管道（FIFO）：可用于无亲缘关系进程
3. 消息队列：消息链表，内核维护
4. 共享内存：最快，需信号量同步
5. 信号量：计数器，用于同步互斥
6. Socket：跨网络通信
7. 信号：异步通知
