# 八股面试题大全 - 消息队列与AI Agent篇

> 覆盖：RabbitMQ、RAG、LangChain、Agent、大模型

## 一、消息队列（RabbitMQ）

### 1. 为什么用消息队列？

**答案**：

1. **异步**：非核心逻辑异步处理，提升响应速度（如本项目预约成功后发消息通知）
2. **解耦**：生产者和消费者不直接依赖，通过MQ通信
3. **削峰**：高峰期请求入队，消费者按能力消费，保护下游
4. **广播**：一个消息可被多个消费者消费

**缺点**：
- 系统复杂度增加
- 消息一致性问题
- 运维成本增加

---

### 2. RabbitMQ的核心概念？

**答案**：

- **Producer**：生产者，发送消息
- **Consumer**：消费者，接收消息
- **Queue**：队列，存储消息
- **Exchange**：交换机，接收生产者消息，路由到队列
- **Binding**：绑定，交换机和队列的绑定关系，含路由键
- **RoutingKey**：路由键，交换机根据路由键路由消息
- **VHost**：虚拟主机，隔离环境

**交换机类型**：
- Direct：精确匹配路由键
- Topic：通配符匹配（*匹配一个词，#匹配多个词）
- Fanout：广播，所有绑定队列都收到
- Headers：根据Header匹配（少用）

**本项目使用Topic交换机**，路由键如message.patient.notify、ai.task等。

---

### 3. 如何保证消息不丢失？

**答案**：从三个环节保证：

**1. 生产者不丢失**：
- 开启Publisher Confirm（生产者确认），消息到达Exchange后回调
- 开启Publisher Returns，消息未路由到队列时回调
- 失败重试 + 本地消息表兜底

**2. MQ不丢失**：
- 队列持久化（durable=true）
- 消息持久化（deliveryMode=2）
- 集群镜像队列

**3. 消费者不丢失**：
- 手动ACK（acknowledge-mode=manual）
- 处理成功后才ack
- 处理失败nack重新入队（有限次数，避免死循环）
- 死信队列接收处理失败的消息

---

### 4. 如何保证消息不重复消费？（幂等性）

**答案**：消费者端保证幂等。

**方法**：
1. **唯一消息ID**：消息带唯一ID，消费前查Redis/数据库是否已消费
2. **业务唯一键**：利用业务本身的唯一性（如订单号），数据库唯一索引
3. **状态机**：订单状态只能从特定状态流转，重复消费时状态不匹配则跳过

**本项目**：消息通知有唯一标识，消费时可根据用户ID+消息类型+关联ID去重。

---

### 5. 消息积压怎么办？

**答案**：
1. **临时扩容消费者**：增加消费者实例数量
2. **批量消费**：提高单条消费效率
3. **优化消费逻辑**：减少IO操作，异步处理非核心逻辑
4. **临时队列转发**：将积压消息转发到新队列，用更多消费者处理
5. **丢弃非重要消息**：极端情况下，非核心消息可丢弃

---

### 6. 死信队列是什么？

**答案**：死信队列（DLX，Dead Letter Exchange）用于处理无法被正常消费的消息。

**消息进入死信队列的条件**：
1. 消费者拒绝消息（basicNack/basicReject）且requeue=false
2. 消息TTL过期
3. 队列达到最大长度

**本项目设计**：
- 所有业务队列配置死信交换机和死信路由键
- 消费失败重试3次后进入死信队列
- 死信队列有专门消费者记录日志并告警

---

### 7. RabbitMQ如何实现延迟队列？

**答案**：两种方式：

1. **TTL + 死信队列**：
   - 消息发送到设置了TTL的队列
   - 消息过期后进入死信交换机
   - 死信队列消费者消费到期消息

2. **延迟队列插件（rabbitmq-delayed-message-exchange）**：
   - 消息带延迟时间
   - 插件延迟后路由到目标队列

**本项目**：订单超时使用Redisson延迟队列（Redis方案），同时RabbitMQ预留了死信队列方案。

---

### 8. RabbitMQ和Kafka的区别？

**答案**：

| 特性 | RabbitMQ | Kafka |
|------|----------|-------|
| 定位 | 传统消息代理 | 分布式流平台 |
| 模型 | Exchange+Queue | Topic+Partition |
| 吞吐量 | 万级 | 百万级 |
| 延迟 | 微秒级 | 毫秒级 |
| 消息顺序 | 队列内有序 | Partition内有序 |
| 消息确认 | 手动ACK | Offset提交 |
| 适用场景 | 业务消息、路由复杂 | 日志、大数据、流处理 |

## 二、AI / LangChain / RAG

### 9. 什么是RAG？为什么需要RAG？

**答案**：RAG（Retrieval-Augmented Generation，检索增强生成），先从知识库检索相关文档，再将文档作为上下文交给LLM生成答案。

**为什么需要RAG**：
1. **解决知识截止问题**：LLM训练数据有截止日期，无法获取最新知识
2. **解决私有知识问题**：企业内部文档、病历等LLM没训练过
3. **减少幻觉**：基于检索到的事实生成，更可靠
4. **可溯源**：答案可追溯到具体文档
5. **成本低**：比微调成本低，知识更新只需更新知识库

**本项目RAG流程**：
1. 医疗文档切分 → BGE嵌入模型向量化 → 存入ChromaDB
2. 用户问题 → 向量化 → 相似度检索Top-K
3. 检索结果格式化 → 注入System Prompt
4. LLM基于上下文生成答案

---

### 10. RAG的完整流程？

**答案**：

**离线阶段（索引构建）**：
1. 文档加载（PDF/Word/Text）
2. 文档切分（按字符数/语义/递归切分）
3. 文本向量化（Embedding模型）
4. 向量存入向量数据库（ChromaDB/Pinecone/Milvus）

**在线阶段（检索生成）**：
1. 用户问题向量化
2. 向量数据库相似度检索（Top-K）
3. 检索结果重排序（Rerank，可选）
4. 构建Prompt（System + Context + Question）
5. LLM生成答案
6. 返回答案 + 引用来源

---

### 11. 文档切分（Chunking）的策略？

**答案**：

1. **固定大小切分**：按字符数切分，带重叠（overlap），简单常用
2. **递归字符切分**：按分隔符优先级（\n\n→\n→。→空格）递归切分，保持语义完整
3. **语义切分**：根据语义相似度切分，更智能但慢
4. **结构化切分**：按Markdown标题、代码块等结构切分
5. **Agentic切分**：用LLM判断切分点

**关键参数**：
- chunk_size：每块大小（通常500-1000 token）
- chunk_overlap：重叠大小（通常10%-20%，保证上下文连续）

---

### 12. 向量数据库有哪些？ChromaDB？

**答案**：

| 向量数据库 | 特点 | 适用场景 |
|-----------|------|----------|
| ChromaDB | 轻量级，本地文件存储，易上手 | 开发/小型项目 |
| Milvus | 分布式，高性能，云原生 | 生产/大规模 |
| Pinecone | 全托管，Serverless | 不想运维 |
| Weaviate | 开源，支持混合检索 | 中等规模 |
| Qdrant | Rust编写，高性能 | 生产 |
| PGVector | PostgreSQL扩展 | 已有PG的项目 |
| FAISS | Facebook开源，库而非服务 | 研究/原型 |

**ChromaDB**（本项目使用）：
- 轻量级，持久化到本地文件
- 支持余弦相似度、欧氏距离
- 支持元数据过滤
- 适合中小规模和开发环境

---

### 13. 什么是Embedding？常见的中文Embedding模型？

**答案**：Embedding（嵌入）是将文本转换为固定维度的向量，语义相近的文本向量距离近。

**常见中文Embedding模型**：
- BGE系列（BAAI）：bge-small-zh、bge-base-zh、bge-large-zh（本项目使用bge-small-zh）
- M3E：m3e-base、m3e-large
- text2vec：text2vec-base-chinese
- 通义千问Embedding、豆包Embedding（API）

**评估指标**：
- 检索召回率（Recall@K）
- MRR（平均倒数排名）
- NDCG（归一化折损累计增益）

---

### 14. 什么是Agent？和普通LLM调用的区别？

**答案**：Agent（智能体）是能自主规划、使用工具、执行任务的LLM应用。

**普通LLM调用**：输入Prompt → 输出答案，单轮，无工具使用能力。

**Agent**：
1. **规划（Planning）**：分解复杂任务为子步骤
2. **记忆（Memory）**：短期记忆（对话历史）+ 长期记忆（知识库）
3. **工具使用（Tool Use）**：调用外部工具（搜索、数据库、API）
4. **反思（Reflection）**：评估结果，自我修正

**本项目Agent架构**：ReAct模式（推理+行动）
- Reasoning：LLM思考需要什么信息
- Acting：调用工具获取信息
- Observation：观察工具结果
- 循环直到得到最终答案

---

### 15. ReAct模式是什么？

**答案**：ReAct = Reasoning + Acting，是一种Agent推理框架。

**流程**：
```
Thought: 我需要查询患者的预约记录
Action: query_appointments(patient_id=1)
Observation: 患者有2条待就诊预约...
Thought: 我还需要查询高血压的诊疗指南
Action: medical_knowledge_search(query="高血压诊断标准")
Observation: 高血压诊断标准是...
Thought: 信息足够了，我来综合回答
Final Answer: 根据您的预约记录和医学指南...
```

**优点**：
- 可解释性强（每步都有思考过程）
- 能处理复杂任务（多步推理+工具调用）
- 减少幻觉（基于工具返回的事实）

---

### 16. Function Calling（工具调用）的原理？

**答案**：Function Calling是LLM的一种能力，模型能根据用户问题决定是否调用工具，并生成结构化的工具调用参数。

**流程**：
1. 开发者定义工具的JSON Schema（名称、描述、参数）
2. 将工具定义和用户问题一起发给LLM
3. LLM判断需要调用工具时，返回tool_calls（工具名+参数JSON）
4. 应用程序执行工具，将结果返回给LLM
5. LLM基于工具结果生成最终答案

**本项目7个工具**：
- query_patient_info：查询患者信息
- query_appointments：查询预约记录
- query_medical_records：查询电子病历
- query_drug_info：查询药品信息
- query_department_doctors：查询科室医生
- medical_knowledge_search：医学知识检索（RAG）
- calculate_drug_dosage：计算用药剂量

### 18. 什么是Prompt Engineering？常用技巧？

**答案**：Prompt Engineering是设计和优化提示词以提升LLM输出质量的技术。

**常用技巧**：
1. **角色设定**：让LLM扮演特定角色（如"你是一名专业的医疗助手"）
2. **Few-shot**：给出几个示例
3. **CoT（思维链）**："让我们一步步思考"，引导模型推理
4. **结构化输出**：要求JSON/Markdown格式
5. **上下文注入**：提供相关背景信息（RAG）
6. **约束条件**：明确限制（如"不超过200字"、"不要编造"）
7. **自我一致性**：多次采样取多数结果

**本项目System Prompt设计要点**：
- 明确角色（医疗智能助手）
- 列出能力和工具使用规范
- 强调安全原则（不替代医生、急症提醒）
- 规定回答格式

---

### 19. LLM的幻觉（Hallucination）是什么？如何减少？

**答案**：幻觉指LLM生成看似合理但实际错误或编造的内容。

**减少幻觉的方法**：
1. **RAG**：基于检索到的事实生成，本项目核心手段
2. **Prompt约束**：明确要求"只根据提供的资料回答，不知道就说不知道"
3. **Few-shot**：给出正确示例
4. **温度调低**：temperature=0.3（本项目设置），减少随机性
5. **引用来源**：要求答案标注引用来源
6. **事实校验**：用工具或另一个LLM验证答案
7. **结构化输出**：限制输出格式，减少自由发挥

### 20. 什么是Token？如何计算？

**答案**：Token是LLM处理文本的基本单位，不是字也不是词。
- 英文：约4个字符=1个token，1个词≈1.3个token
- 中文：约1-2个汉字=1个token

**计算工具**：tiktoken（OpenAI）、transformers的tokenizer

**本项目记录**：每次LLM调用记录prompt_tokens、completion_tokens、total_tokens，用于成本统计和性能分析。

### 21. 大模型的微调方式？

**答案**：

1. **全量微调（Full Fine-tuning）**：更新所有参数，效果好但成本高
2. **参数高效微调（PEFT）**：
   - LoRA：低秩适配，只训练少量参数（秩分解矩阵），最常用
   - QLoRA：量化+LoRA，更省显存
   - Prefix Tuning：只训练前缀参数
   - Prompt Tuning：只训练连续提示向量
3. **RLHF**：基于人类反馈的强化学习，对齐人类偏好

**RAG vs 微调**：
- RAG：知识更新容易，成本低，可溯源，适合知识密集型
- 微调：改变模型风格/行为，适合特定领域风格适配
- 实际中常结合使用

### 22. 流式输出（SSE）的原理？

**答案**：SSE（Server-Sent Events）是服务器向客户端单向推送数据的HTTP协议。

**特点**：
- 基于HTTP，长连接
- 服务器主动推送，客户端监听
- 数据格式：`data: xxx\n\n`
- 自动重连

**本项目AI流式对话**：
- Python Agent的`/api/agent/chat/stream`接口
- LLM流式返回每个token
- 通过SSE实时推送到前端
- 前端逐字渲染，提升体验

**vs WebSocket**：
- SSE：单向（服务器→客户端），基于HTTP，简单
- WebSocket：双向，更复杂，适合需要客户端频繁发送的场景

### 23. 如何评估RAG系统的效果？

**答案**：

**检索阶段评估**：
- Recall@K：前K个结果中包含正确答案的比例
- Precision@K：前K个结果中相关结果的比例
- MRR：第一个相关结果的排名倒数
- NDCG：考虑排名位置的相关性评分

**生成阶段评估**：
- 忠实度（Faithfulness）：答案是否基于检索内容
- 相关性（Relevance）：答案是否回答了问题
- 正确性（Correctness）：答案是否准确
- 人工评估：专业医生打分

**工具**：RAGAS（RAG Assessment）框架，自动评估。

### 24. 多轮对话的记忆管理？

**答案**：

**短期记忆**：
- 滑动窗口：保留最近N轮对话（本项目默认10轮）
- Token计数：保留不超过Token上限的对话
- 摘要记忆：用LLM将历史对话压缩为摘要

**长期记忆**：
- 向量数据库存储历史对话，检索相关历史
- 用户画像：提取用户偏好、病史等结构化信息

**本项目实现**：
- Redis List存储对话历史，24小时过期
- 滑动窗口取最近10轮
- session_id区分不同会话

### 25. AI Agent在医疗场景的安全考虑？

**答案**：

1. **免责声明**：所有回答末尾添加"仅供参考，不能替代医生诊断"
2. **不直接诊断**：提供参考信息，不做最终诊断结论
3. **不提供处方**：不直接给出具体用药剂量（除工具计算外）
4. **急症识别**：识别胸痛、呼吸困难等急症关键词，立即建议120
5. **内容审核**：输入输出安全过滤，防止不当内容
6. **调用限流**：防止滥用和成本失控
7. **对话审计**：所有对话记录到ai_conversation表，可追溯
8. **用户反馈**：点赞/点踩功能，持续优化
