# 八股面试题大全 - MySQL与Redis篇

> 覆盖：MySQL索引、事务、锁、优化；Redis数据结构、持久化、缓存、分布式锁

---

## 一、MySQL

### 1. MySQL的索引类型？

**答案**：

**按数据结构分**：
- B+Tree索引（InnoDB默认）
- Hash索引（Memory引擎，Memory精确匹配快）
- 全文索引（FULLTEXT，MyISAM/InnoDB 5.6+）
- R-Tree索引（空间数据）

**按物理存储分**：
- 聚簇索引：索引和数据在一起，叶子节点存整行数据（主键索引就是聚簇索引）
- 非聚簇索引（二级索引）：叶子节点存主键值，需要回表查询

**按字段数分**：
- 单列索引
- 联合索引（最左前缀匹配）

---

### 2. 为什么用B+Tree而不是B树/红黑树/Hash？

**答案**：

**B+Tree vs B树**：
- B+Tree非叶子节点不存数据，只存索引，能存更多索引，树更矮
- B+Tree叶子节点用双向链表连接，范围查询效率高
- B树每个节点都存数据，查询不稳定

**B+Tree vs 红黑树**：
- 红黑树是二叉树，数据量大时树很高，IO次数多
- B+Tree是多叉树，扇出大，树高通常3-4层，IO少

**B+Tree vs Hash**：
- Hash等值查询O(1)，但不支持范围查询、排序、模糊查询
- B+Tree支持范围查询、排序、最左前缀匹配

---

### 3. 聚簇索引和非聚簇索引的区别？回表？

**答案**：

**聚簇索引**（主键索引）：
- 叶子节点存储完整行数据
- 一个表只有一个聚簇索引
- 数据按主键顺序物理存储

**非聚簇索引**（二级索引）：
- 叶子节点存储主键值
- 一个表可以有多个
- 查询时先找到主键，再用主键去聚簇索引查完整数据 → **回表**

**覆盖索引**：查询的字段都在索引中，不需要回表。如`SELECT name FROM user WHERE name = 'xxx'`，name是索引列。

---

### 4. 最左前缀匹配原则？

**答案**：联合索引(a,b,c)，查询条件必须从最左列开始，不能跳过。

**能命中索引的情况**：
- WHERE a = ?
- WHERE a = ? AND b = ?
- WHERE a = ? AND b = ? AND c = ?
- WHERE a = ? AND c = ?（只用到a，c用不到）

**不能命中的情况**：
- WHERE b = ?（跳过a）
- WHERE b = ? AND c = ?（跳过a）

**特殊情况**：
- 范围查询（>、<、between）之后的列用不到索引
- 函数操作、隐式类型转换会导致索引失效

---

### 5. 索引失效的场景？

**答案**：
1. 对索引列使用函数、运算（WHERE YEAR(create_time) = 2026）
2. 隐式类型转换（字符串列用数字查询）
3. LIKE以%开头（LIKE '%abc'）
4. OR连接的条件中有非索引列
5. 联合索引不满足最左前缀
6. 优化器判断全表扫描更快（数据量少时）
7. NOT、!=、<>可能失效
8. IS NULL / IS NOT NULL（取决于数据分布）

---

### 6. MySQL事务的ACID？

**答案**：
- **原子性（Atomicity）**：事务要么全部成功，要么全部失败。由undo log保证。
- **一致性（Consistency）**：事务前后数据从一个一致状态到另一个一致状态。由其他三个特性共同保证。
- **隔离性（Isolation）**：并发事务互不干扰。由锁+MVCC保证。
- **持久性（Durability）**：事务提交后数据永久保存。由redo log保证。

---

### 7. redo log和undo log的区别？

**答案**：

| 特性 | redo log | undo log |
|------|----------|----------|
| 作用 | 崩溃恢复，保证持久性 | 回滚，保证原子性，MVCC |
| 内容 | 物理日志，记录页的修改 | 逻辑日志，记录反向操作 |
| 写入时机 | 修改后写入，先写日志再写磁盘 | 修改前写入 |
| 循环写 | 固定大小，循环覆盖 | 追加写 |
| 所属 | InnoDB引擎层 | InnoDB引擎层 |

**WAL（Write-Ahead Logging）**：先写日志，再写磁盘。保证即使宕机，重启后可通过redo log恢复。

---

### 8. binlog、redo log、undo log的区别？

**答案**：
- **binlog**：Server层，逻辑日志，记录SQL语句或行变更，用于主从复制和数据恢复，追加写
- **redo log**：InnoDB引擎层，物理日志，记录页修改，用于崩溃恢复，循环写
- **undo log**：InnoDB引擎层，逻辑日志，记录反向操作，用于回滚和MVCC

**两阶段提交**：为保证redo log和binlog一致，采用两阶段提交：
1. prepare阶段：写redo log，标记为prepare
2. 写binlog
3. commit阶段：redo log标记为commit

---

### 9. MVCC的原理？

**答案**：MVCC（多版本并发控制），通过版本链实现读写不阻塞，提高并发性能。

**实现要素**：
1. **隐藏字段**：每行有trx_id（创建/修改的事务ID）、roll_pointer（指向undo log的指针）
2. **undo log版本链**：每次修改生成一条undo log，通过roll_pointer连成链
3. **ReadView**：一致性视图，包含：
   - m_ids：活跃事务ID列表
   - min_trx_id：最小活跃事务ID
   - max_trx_id：下一个要分配的事务ID
   - creator_trx_id：创建ReadView的事务ID

**可见性判断**（从版本链头开始找）：
- trx_id == creator_trx_id：可见（自己修改的）
- trx_id < min_trx_id：可见（已提交）
- trx_id >= max_trx_id：不可见（未开始）
- min_trx_id <= trx_id < max_trx_id：在m_ids中则不可见，不在则可见

**RC和RR的区别**：
- RC：每次SELECT都生成新的ReadView
- RR：第一次SELECT生成ReadView，之后复用（可重复读）

---

### 10. MySQL的锁？

**答案**：

**按粒度分**：
- 全局锁：FTWRL（Flush Tables With Read Lock），全库只读，备份用
- 表级锁：表锁、元数据锁（MDL）、意向锁
- 行级锁：Record Lock（记录锁）、Gap Lock（间隙锁）、Next-Key Lock（记录+间隙）

**按模式分**：
- 共享锁（S锁）：读锁，共享，SELECT ... LOCK IN SHARE MODE
- 排他锁（X锁）：写锁，互斥，UPDATE/DELETE/SELECT ... FOR UPDATE

**间隙锁**：RR隔离级别下，防止幻读，锁定索引之间的间隙。
**Next-Key Lock**：记录锁+间隙锁，左开右闭区间，RR默认加锁方式。

---

### 11. 幻读是什么？如何解决？

**答案**：幻读指同一事务中两次相同范围查询，第二次看到了第一次没有的行（其他事务插入了新行）。

**解决方式**：
- SERIALIZABLE：全表锁，性能差
- RR + Next-Key Lock：间隙锁锁定范围，防止插入（InnoDB默认RR已解决幻读）
- MVCC：快照读通过版本链避免幻读

**快照读 vs 当前读**：
- 快照读：普通SELECT，读快照版本，不加锁
- 当前读：SELECT ... FOR UPDATE / LOCK IN SHARE MODE / UPDATE / DELETE，读最新版本，加锁

---

### 12. 如何优化SQL？

**答案**：

1. **索引优化**：
   - 为WHERE、JOIN、ORDER BY、GROUP BY的列建索引
   - 联合索引遵循最左前缀
   - 避免索引失效
   - 使用覆盖索引避免回表

2. **查询优化**：
   - 避免SELECT *，只查需要的列
   - 小表驱动大表（JOIN）
   - 分页优化：深分页用子查询/游标
   - 用EXISTS代替IN（大数据量）
   - 避免在索引列上用函数

3. **表结构优化**：
   - 选择合适的数据类型
   - 避免NULL（NOT NULL + 默认值）
   - 大字段拆表
   - 适当反范式（冗余字段减少JOIN）

4. **架构优化**：
   - 读写分离
   - 分库分表
   - 缓存（Redis）

---

### 13. 慢查询如何排查？

**答案**：
1. 开启慢查询日志：slow_query_log=1，long_query_time=1
2. 用mysqldumpslow或pt-query-digest分析慢日志
3. EXPLAIN分析执行计划
4. SHOW PROFILE分析执行耗时
5. 优化索引或SQL

**EXPLAIN关键字段**：
- type：访问类型（system>const>eq_ref>ref>range>index>ALL），至少要到range
- key：实际使用的索引
- rows：扫描行数
- Extra：Using index（覆盖索引）、Using filesort（需优化）、Using temporary（需优化）

---

### 14. 分库分表的方式？

**答案**：

**垂直分库**：按业务模块拆分，如用户库、订单库、商品库
**垂直分表**：大字段拆到扩展表，冷热数据分离
**水平分库**：同一个表的数据按规则分到多个库
**水平分表**：同一个库内表拆分为多个子表

**分片算法**：
- 范围分片：按时间/ID范围，易扩容，热点问题
- 哈希分片：取模，均匀，扩容需迁移数据
- 一致性哈希：扩容影响小

**中间件**：ShardingSphere（本项目预留）、MyCat

## 二、Redis

### 15. Redis的数据结构？

**答案**：

| 类型 | 底层实现 | 应用场景 |
|------|----------|----------|
| String | SDS（简单动态字符串） | 缓存、计数器、分布式锁、Session |
| List | 压缩列表/双向链表 | 消息队列、最新列表 |
| Hash | 压缩列表/哈希表 | 对象缓存、购物车 |
| Set | 哈希表/整数数组 | 去重、交集并集差集、标签 |
| ZSet | 压缩列表/跳表 | 排行榜、延迟队列、范围查询 |
| Bitmap | String位操作 | 签到、布隆过滤器、用户在线状态 |
| HyperLogLog | 稀疏矩阵/稠密矩阵 | 基数统计（UV） |
| Geo | ZSet | 地理位置、附近的人 |
| Stream | 列表+Radtree | 消息队列（5.0+） |

---

### 16. Redis为什么快？

**答案**：
1. **纯内存操作**：数据在内存，读写纳秒级
2. **单线程模型**：避免线程切换和锁竞争（6.0后网络IO多线程，命令执行仍单线程）
3. **IO多路复用**：epoll，单线程处理大量并发连接
4. **高效数据结构**：SDS、跳表、压缩列表等
5. **持久化异步**：不阻塞主进程

---

### 17. Redis的持久化？

**答案**：

**RDB（快照）**：
- 定时将内存数据快照保存到磁盘
- SAVE（阻塞）/ BGSAVE（fork子进程，非阻塞）
- 优点：文件小，恢复快
- 缺点：可能丢失最后一次快照后的数据

**AOF（追加日志）**：
- 记录每个写命令，追加到文件
- 三种刷盘策略：always（每条）、everysec（每秒，默认）、no（OS控制）
- 优点：数据安全，最多丢1秒
- 缺点：文件大，恢复慢，需重写（AOF Rewrite）压缩

**混合持久化（4.0+）**：AOF重写时，前半段RDB格式，后半段AOF格式，兼顾恢复速度和数据安全。

**生产环境建议**：开启混合持久化，RDB做全量备份，AOF做增量。

---

### 18. Redis的过期键删除策略？

**答案**：

1. **惰性删除**：访问key时才检查是否过期，过期则删除。CPU友好，内存不友好。
2. **定期删除**：每隔一段时间随机抽取一批key检查，删除过期的。平衡CPU和内存。
3. **内存淘汰**：内存满时触发淘汰策略。

**Redis实际使用**：惰性删除 + 定期删除 配合。

---

### 19. Redis的内存淘汰策略？

**答案**：8种策略（默认noeviction）：

| 策略 | 说明 |
|------|------|
| noeviction | 不淘汰，写操作报错（默认） |
| allkeys-lru | 所有key中，LRU淘汰最久未使用 |
| allkeys-lfu | 所有key中，LFU淘汰最少使用 |
| allkeys-random | 所有key中随机淘汰 |
| volatile-lru | 设置了过期时间的key中，LRU淘汰 |
| volatile-lfu | 设置了过期时间的key中，LFU淘汰 |
| volatile-random | 设置了过期时间的key中随机淘汰 |
| volatile-ttl | 设置了过期时间的key中，淘汰最早过期的 |

**LRU vs LFU**：
- LRU：最近最少使用，按时间
- LFU：最不经常使用，按访问频率（4.0+），解决偶发热点key污染问题

### 20. 缓存穿透、缓存击穿、缓存雪崩？

**答案**：

**缓存穿透**：查询不存在的数据，缓存和数据库都没有，每次请求都打到数据库。
- 解决：缓存空值（短过期时间）、布隆过滤器（提前过滤不存在的key）

**缓存击穿**：某个热点key过期，大量请求同时打到数据库。
- 解决：互斥锁（Redis分布式锁，只让一个请求查库）、热点key永不过期（逻辑过期）

**缓存雪崩**：大量key同时过期，或Redis宕机，请求全部打到数据库。
- 解决：过期时间加随机值、Redis集群高可用、服务降级熔断、多级缓存

---

### 21. Redis分布式锁的实现？

**答案**：

**基本实现**：SET key value NX EX timeout
- NX：key不存在才设置（互斥）
- EX：过期时间（防死锁）

**存在的问题**：
1. 业务执行超时，锁过期释放，其他线程获取锁 → 锁续期（看门狗）
2. 线程A释放了线程B的锁 → value存唯一标识（UUID），释放时校验
3. 主从切换导致锁丢失 → RedLock（多数节点加锁成功）

**Redisson分布式锁**（本项目使用）：
- 可重入：Hash结构，field=线程ID，value=重入次数
- 看门狗：默认30秒过期，每10秒续期
- 支持公平锁、读写锁、联锁、红锁
- 底层Lua脚本保证原子性

### 22. Redisson延迟队列的实现？

**答案**（本项目订单超时使用）：

**原理**：基于Redis的ZSet实现。
1. 消息体存到一个队列（List）
2. 消息ID和到期时间存到ZSet（score=到期时间戳）
3. 后台线程定时轮询ZSet，取出到期的消息
4. 从队列中取出消息消费

**Redisson的RDelayedQueue**：
- 封装了上述逻辑
- offer(msg, delay, timeUnit)投递延迟消息
- 消费者从目标队列take()阻塞获取
- 底层使用Redis的ZSet + List + 发布订阅

**vs RabbitMQ死信队列**：
- Redisson：简单，不需要额外中间件，但可靠性依赖Redis
- RabbitMQ：专业消息队列，可靠性高，有死信、重试、持久化

### 23. Redis和MySQL双写一致性？

**答案**：

**方案对比**：

1. **先更新数据库，再删除缓存**（推荐）：
   - 缓存删除失败可重试（消息队列）
   - 并发下可能有短暂不一致，但最终一致

2. **先删除缓存，再更新数据库**：
   - 并发下可能导致缓存旧数据（读请求在删除后、更新前回填了旧值）
   - 需延迟双删：删缓存→更新DB→延迟再删缓存

3. **通过MQ异步更新缓存**：
   - 订阅binlog（Canal），异步更新缓存
   - 解耦，最终一致

**本项目**：读多写少场景，采用"先更新数据库，再删除缓存"策略。

### 24. Redis的大key和热key问题？

**答案**：

**大key**：value很大（如10MB的String、百万元素的Hash）
- 危害：网络阻塞、内存不均、删除阻塞、迁移困难
- 解决：拆分大key（Hash分桶、List分页）、压缩value、异步删除（UNLINK）

**热key**：访问量极高的key（如秒杀商品）
- 危害：打垮Redis单节点、网络带宽瓶颈
- 解决：本地缓存（Caffeine，本项目L1缓存）、热key分散（加后缀存多份）、读写分离

---

### 25. Redis的集群方案？

**答案**：

1. **主从复制**：一主多从，主写从读，主挂了需手动切换
2. **哨兵模式（Sentinel）**：主从+哨兵，自动故障转移，高可用
3. **Cluster集群**：数据分片（16384个slot），去中心化，水平扩展

**Redis Cluster**：
- 16384个哈希槽分配给各主节点
- key通过CRC16(key) % 16384定位槽
- 每个主节点有从节点做备份
- 支持在线扩缩容
